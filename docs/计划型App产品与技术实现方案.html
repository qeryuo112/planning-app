PRODUCT & TECHNICAL PROPOSAL

计划型 App 产品与技术实现方案

围绕“目标—计划—执行—反馈”的 AI 个人成长管理产品

版本：MVP 方案讨论稿
日期：2026 年 8 月

执行摘要

建议先围绕一个高频主场景，跑通“创建目标 → AI 生成 7 天计划 → 用户确认 → 今日执行 → 每日打卡 → 周复盘 → AI 调整”的闭环，再扩展复杂协作、社交和生态集成。

1. 项目概述

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

本项目拟构建一款以“计划—执行—反馈—调整”为核心闭环的个人计划型 App。产品体验参考滴答清单的任务与日程管理能力，同时吸收 Keep 健身计划的阶段性目标、每日打卡、连续完成与进度反馈机制，并在核心流程中内联 AI，让用户可以用自然语言生成计划、拆解目标、调整任务和复盘执行情况。

产品不应只是“任务清单 + 聊天机器人”，而应成为一个可持续执行的计划系统：

  • 上层管理方向：长期目标、中期项目、短期计划。
  • 中层安排节奏：日程、周期任务、时间块和优先级。
  • 下层推动执行：每日任务、打卡、连续记录、进度和复盘。
  • AI 负责降低规划门槛，但最终计划必须可编辑、可解释、可撤销。

2. 产品定位与目标用户

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

2.1 产品定位

定位为“AI 驱动的个人目标与行动管理工具”，核心价值是把模糊愿望转化为可执行的每日行动，并通过打卡反馈帮助用户保持节奏。

2.2 目标用户

  1. 有明确成长诉求，但不擅长拆解计划的个人用户。
  2. 同时管理学习、工作、健身、证书、阅读等多个方向的用户。
  3. 使用过待办工具，但经常“列了很多任务，真正完成很少”的用户。
  4. 希望通过 AI 快速生成计划，又不希望把控制权完全交给 AI 的用户。

2.3 MVP 成功标准

  • 用户可在 3 分钟内创建一个目标，并得到一份可执行的首周计划。
  • 用户每天打开 App 能快速看到“今天最重要的 3 件事”。
  • 完成任务后能即时看到目标进度、连续打卡和阶段反馈。
  • 计划可被用户随时调整，AI 生成内容不会覆盖用户已有数据。
  • 7 日留存、首周任务完成率和计划执行率成为第一阶段核心指标。

3. 核心产品闭环

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

3.1 目标分层

目标采用三级结构：

  • 长期目标：通常为 6 个月至 3 年，回答“我想成为谁/完成什么”。
  • 中期目标：通常为 1 至 6 个月，回答“这一阶段要达成什么结果”。
  • 短期目标：通常为 1 至 4 周，回答“近期要完成什么里程碑”。

建议采用“目标—项目—任务—打卡记录”的层级，而不是把所有内容都当成任务：

  • 目标：结果导向，例如“通过英语四级”。
  • 项目：阶段性计划，例如“完成四级备考第一阶段”。
  • 任务：具体行动，例如“背 50 个高频词”。
  • 打卡：某次执行事实，例如“2026-08-11 完成背词 50 个”。

3.1.1 习惯（Habit）的独立维度

习惯与目标体系解耦，是“计划型 App”区别于普通待办工具的核心差异。习惯不直接服务于某个目标的截止日期，而是持续性的自我约束：

  • 习惯：独立于 Goal-Project-Task 体系，例如“每天喝水 2L”“23:00 前睡觉”“晨间冥想 10 分钟”。
  • 习惯可选择性关联目标（如“每日背词”同时服务于“通过四级”目标），但本身拥有独立的频率规则、最低完成标准和连续记录。
  • 打卡记录（Checkin）同时支持关联 TaskInstance 和 Habit，或两者之一，保证统计口径统一。

为什么独立习惯很重要：用户的大量日常行为（作息、饮食、运动习惯）并不天然属于某个“项目”，但如果缺失这部分，App 就只是任务清单而非成长系统。

3.2 日程与任务

日程是“时间安排”，任务是“待完成事项”，二者需要关联但不能混为一谈：

  • 无固定时间的任务进入收件箱或任务列表。
  • 有明确时间段的任务进入日历时间块。
  • 周期任务自动生成未来实例，但保留任务模板。
  • 任务可关联目标、项目、标签、优先级、预计时长和能量要求。

3.3 每日执行与打卡

每日首页建议提供四个区域：

  1. 今日进度：完成任务数、目标进度、连续打卡天数。
  2. 今日重点：由用户或 AI 选出的 1—3 个关键任务。
  3. 计划时间线：按时间排列的日程和任务。
  4. 快速打卡：一键完成、跳过、延期、补记，并记录简单备注。

打卡不等于“简单勾选”。需要记录：完成时间、完成状态、实际耗时、完成质量、备注、是否补打卡。这样后续 AI 才能根据真实执行情况调整计划。

3.3.1 能量/精力管理

任务除了时间属性，还应匹配用户的精力曲线，避免“高能量任务全堆到晚上”：

  • 用户在设置中定义个人精力曲线（如上午高能量、下午中能量、晚上低能量），或让 AI 根据历史完成时间推断。
  • 每个任务标注 energy_level：高（深度工作）、中（常规任务）、低（机械性任务）。
  • AI 排程时优先将高能量任务匹配到用户高精力时段，低能量任务填充碎片时间。
  • 今日视图增加“能量预算”概览：高能量任务已分配时长 / 用户高精力时段总时长，防止过载。

3.4 反馈与复盘

每天结束时，系统可以提供轻量复盘：

  • 今天完成了什么？
  • 哪项任务延期了？原因是什么？
  • 明天最重要的一件事是什么？
  • 当前计划是否过载？

每周生成周报：完成率、延期率、连续打卡、目标进度、最常见阻塞原因以及下一周建议。

4. 功能模块设计

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

4.1 首页 / 今日

  • 今日日期与总体完成率。
  • 今日重点任务。
  • 日程时间线。
  • 目标进度卡片。
  • 连续打卡与阶段勋章。
  • AI 快捷入口：生成今日安排、压缩计划、重新排程、解释目标。

4.2 收件箱

所有快速记录的想法、任务和 AI 识别结果先进入收件箱，再由用户整理到目标、项目、日程或清单中。收件箱是降低录入成本的关键模块。

4.3 任务管理

建议支持：

  • 清单、看板、日历三种视图。
  • 子任务、依赖关系、优先级、标签、估时。
  • 截止时间与提醒。
  • 重复任务规则。
  • 延期、跳过、归档、批量操作。
  • 任务模板，例如“晨间学习”“周末长跑”。

4.4 目标中心

目标详情页应展示：

  • 目标描述、截止日期、成功标准。
  • 长期 / 中期 / 短期层级关系。
  • 当前里程碑和完成比例。
  • 关联项目与任务。
  • 计划趋势、打卡日历和风险提示。
  • AI 重新拆解与调整入口。

4.5 打卡计划

参考 Keep 的计划感，但避免过度游戏化：

  • 计划周期：7 天、14 天、30 天、90 天或自定义。
  • 每日动作：动作名称、目标量、预计时长、最低完成标准。
  • 完成状态：完成、部分完成、跳过、补打卡。
  • 连续记录：连续天数、最佳纪录、阶段完成率。
  • 进度算法：同时展示“任务完成率”和“目标里程碑完成率”，避免单一百分比误导。

4.6 AI 工作台

AI 不单独做成一个与业务分离的聊天页，而是嵌入目标、任务、日程和复盘场景：

  • 创建目标时：把愿望变成 SMART 目标。
  • 目标详情页：拆解里程碑和阶段计划。
  • 今日页：根据可用时间安排今日任务。
  • 任务页：把大任务拆成下一步动作。
  • 延期后：分析原因并重新排程。
  • 周复盘：总结执行情况并提出调整建议。

5. AI 计划生成的实现方式

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

5.1 推荐交互流程

  1. 用户输入自然语言，例如“我想在 3 个月内通过英语四级，每天只有 40 分钟”。
  2. AI 先提取结构化信息：目标、周期、约束、可用时间、已有基础、偏好。
  3. 若关键条件缺失，AI 只追问 1—3 个最重要的问题。
  4. AI 输出计划草案：目标、里程碑、周计划、每日任务、预估用时、验收标准。
  5. 用户预览并编辑。
  6. 用户点击“采用计划”后，系统将草案转换成正式目标、项目、任务和日程。
  7. 后续根据打卡与延期情况，AI 生成调整建议，而不是自动修改正式计划。

5.2 结构化输出

不要让 AI 直接输出不可控的富文本。应要求 AI 输出符合 JSON Schema 的计划对象，由服务端校验后再入库。示例结构：

{
  "goal": {
    "title": "通过英语四级",
    "horizon": "medium",
    "start_date": "2026-08-12",
    "due_date": "2026-11-12",
    "success_criteria": ["完成真题训练", "模拟成绩达到目标分数"]
  },
  "milestones": [
    {
      "title": "完成基础词汇与语法",
      "due_date": "2026-09-05",
      "weight": 0.25
    }
  ],
  "tasks": [
    {
      "title": "背诵高频词 50 个",
      "date": "2026-08-12",
      "duration_minutes": 30,
      "energy_level": "medium",
      "repeat_rule": null,
      "milestone_ref": "m1",
      "minimum_standard": "至少背诵 30 个并复习昨日词汇"
    }
  ],
  "habits": [
    {
      "title": "每日复盘 5 分钟",
      "frequency": "daily",
      "preferred_time": "22:00",
      "energy_level": "low"
    }
  ],
  "assumptions": ["用户具备高中英语基础"],
  "warnings": ["若连续 3 天无法完成，应降低每日任务量"],
  "estimated_weekly_load": { "total_minutes": 1260, "high_energy_minutes": 420 }
}

Schema 设计要点：

  • energy_level：每个任务和习惯标注高/中/低能量需求，供排程时匹配精力曲线。
  • minimum_standard：定义最低完成标准，用于连续打卡判定（不必 100% 完成才算打卡成功）。
  • habits：独立输出习惯列表，与任务体系平行。
  • estimated_weekly_load：AI 预估周总负荷，用于与用户可用时间交叉校验，防止过载。

5.3 AI 服务分层

建议采用“模型适配层 + 计划编排层 + 业务执行层”的三层结构：

  • 模型适配层：统一对接不同模型供应商，屏蔽 API 差异、鉴权、限流、重试和流式输出。
  • 计划编排层：负责提示词模板、上下文组装、Schema 校验、计划版本和变更 diff。
  • 业务执行层：把通过校验的计划写入目标、里程碑、任务、日程和提醒。

这样未来可以更换模型，不需要重写产品逻辑。

5.4 提示词设计原则

  • 明确角色：计划教练，而不是泛化聊天助手。
  • 明确约束：时间、频率、难度、已有基础和不可用时段。
  • 明确输出协议：只输出符合 Schema 的 JSON。
  • 明确安全边界：不做医疗诊断，不替代专业建议；涉及健身与健康时给出风险提示。
  • 明确现实性：任务必须可执行，单日总时长不得超过用户可用时间。
  • 明确可解释：每个阶段说明为什么这样拆解。

5.5 计划版本与人工确认

AI 生成的计划必须先保存为 draft，不直接覆盖正式计划。推荐保留：

  • plan_version：计划版本号。
  • source：用户创建、AI 生成、AI 调整、手动编辑。
  • diff：本次变更了哪些目标、任务、时间和权重。
  • approved_by_user：是否经过用户确认。
  • rollback_version：可回退到上一版本。

5.6 领域模板与轻量级个性化（MVP 策略）

MVP 阶段不需要完整 RAG 架构，采用“预置模板 + AI 微调”策略，兼顾可控性与成本：

  • 模板库：预置 5—10 个高质量领域计划模板（如“考研英语 3 个月基础阶段”“30 天居家减脂入门”“CPA 会计科目 60 天计划”）。
  • 模板匹配：用户输入自然语言后，AI 先判断最接近的模板，再基于用户约束（可用时间、基础水平、禁忌条件）做个性化调整。
  • 模板即内容资产：模板本身作为 PlanVersion 的一种 source = "template"，支持版本管理和用户二次编辑。
  • 优势：比纯生成更可控、token 成本更低、输出质量更稳定；同时解决冷启动时空状态问题。

5.7 用户反馈闭环

AI 生成计划不是一次性交付，需要建立“生成 → 执行 → 反馈 → 调优”的闭环：

  • 即时反馈：用户在预览计划草案时，可提供结构化反馈（“太难了”“太简单了”“时间不合适”“某科目权重过低”），作为 user_feedback 存入 PlanVersion。
  • 执行反馈：任务延期、跳过、部分完成时，系统记录原因标签（“时间不够”“难度超预期”“突发事项”“动力不足”）。
  • 用户画像摘要：长期积累后形成轻量级画像（如“该用户倾向于低估任务耗时约 20%”“高能量时段集中在上午”），AI 在生成新计划时自动修正偏差。
  • A/B 提示词测试：不同版本的提示词通过 prompt_version 区分，对比同一模板下的计划采纳率和首周完成率。

5.8 多轮对话与会话管理

实际场景中用户不会一次性说完所有约束，AI 需要支持多轮澄清和追问：

  • AISession 实体：管理多轮对话上下文，与会话绑定的业务场景（如“在目标详情页的对话仅关注该目标”）。
  • 上下文裁剪：限制保留最多 3 轮对话历史，避免 token 成本失控；超出部分由系统生成摘要替代。
  • 澄清策略：AI 提取结构化信息后，若关键条件缺失，只追问 1—3 个最重要的问题（如可用时间、基础水平、截止日期），避免冗长问卷。
  • 流式输出：计划生成过程通过 SSE（Server-Sent Events）实时推送给客户端，减少用户等待焦虑。

6. 进度与打卡算法

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

6.1 任务完成率

任务完成率 = 已完成任务权重之和 / 计划任务权重总和。

如果所有任务权重相同，可以简化为：已完成任务数 / 应完成任务数。延期任务不应直接算作未完成后永久影响总分，应区分“当前执行率”和“历史完成率”。

6.2 目标进度

目标进度不建议只按任务数量计算，可采用加权里程碑：

目标进度 = Σ（里程碑完成度 × 里程碑权重）。

例如：基础阶段 25%、专项训练 35%、模拟验证 40%。这样用户完成关键阶段时，进度反馈更符合真实结果。

6.3 连续打卡

连续打卡应基于“当天达到最低完成标准”计算，而不是要求所有任务全部完成：

  • 完成最低标准：计入连续。
  • 部分完成：显示部分完成，可配置是否计入。
  • 跳过：不计入，但不一定打断长期统计。
  • 补打卡：标记为补记，不建议伪装成自然完成。

6.4 防止挫败感

建议同时展示：

  • 今日完成率。
  • 本周完成率。
  • 目标累计进度。
  • 连续打卡天数。
  • 最近 7 天趋势。

不要只用“连续中断”作为核心反馈，避免用户因一次失败而放弃整个计划。

6.5 执行偏差量化记录

打卡记录不仅是“是否完成”的布尔值，还应量化偏差，为 AI 复盘和调整提供数据基础：

  • 时间偏差：planned_duration vs actual_duration，计算耗时偏差率（如实际用时是预估的 1.5 倍）。
  • 排程偏差：scheduled_date vs actual_completed_date，记录延期天数和频率。
  • 质量自评：用户完成任务时可选 1—5 星主观评分，反映完成质量而非仅完成与否。
  • 能量匹配度：记录任务实际执行时段与标注 energy_level 的匹配情况，验证精力曲线假设。
  • 阻塞原因标签：延期/跳过时选择预设标签（“时间冲突”“难度超预期”“动力不足”“身体不适”“突发事项”），形成可统计的阻塞分布。

这些数据汇总后，周复盘时 AI 可以给出具体建议（如“本周 60% 的任务实际耗时超出预估，建议下周将同类任务预估上调 30%”），而非泛泛而谈。

7. 技术架构建议

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

7.1 推荐技术栈

如果目标是先做跨平台 MVP：

  • 客户端：Flutter 或 React Native。若重视统一 UI 和稳定动画，优先 Flutter；若团队 React/TypeScript 能力强，优先 React Native。
  • 服务端：NestJS / Fastify + TypeScript，或 Go。MVP 推荐 NestJS，便于快速构建模块化 API。
  • 数据库：PostgreSQL，适合目标、任务、日程、版本和统计等关系型数据。
  • 缓存与队列：Redis，用于提醒、异步 AI 任务、限流和短期缓存。
  • 搜索：MVP 可先用 PostgreSQL 全文搜索；数据量增大后再引入 OpenSearch。
  • 对象存储：用于用户附件、计划复盘图片等非结构化数据。
  • 推送：Android / iOS 推送服务，服务端统一封装通知策略。
  • 实时通信：SSE（Server-Sent Events）用于 AI 计划生成的流式输出；WebSocket 用于多端同步状态广播。
  • 可观测性：MVP 阶段至少接入结构化日志（如 Pino/Winston）+ 基础指标（Prometheus + Grafana 或云厂商方案），核心追踪 AI 调用链路（输入/输出 token、耗时、模型版本、是否命中缓存）。
  • 部署：容器化部署，区分开发、测试和生产环境。

7.3 离线与同步

计划类 App 很依赖随手记录和快速打卡，建议从 MVP 就设计基础离线能力：

  • 客户端本地保存今日任务和最近目标。
  • 离线完成任务时记录 operation_id、客户端时间和版本号。
  • 恢复联网后按操作队列同步。
  • 冲突处理优先采用“事件合并 + 用户可见提示”，不要简单覆盖。
  • 打卡记录尽量设计为追加事件，减少并发覆盖。

7.4 可观测性与核心指标

AI 产品必须能回答“为什么 AI 给出了这个计划”，可观测性不是可选项：

  • AI 调用链路：每次调用记录 request_id、模型供应商、模型版本、prompt_version、输入 token、输出 token、耗时、费用、是否命中缓存、是否解析成功。
  • 业务漏斗埋点：核心路径必须可追踪——创建目标 → 生成计划草案 → 用户确认 → 完成首日任务 → 7 日留存。每个节点记录转化率。
  • 计划质量指标：计划采纳率（预览后点击确认的比例）、首周任务完成率、平均延期率、计划调整频率。
  • 用户行为事件：关键操作（创建目标、生成计划、完成任务、延期、跳过、打开 AI 工作台）写入 UserEvent 表，支撑产品分析。
  • 告警规则：AI 接口错误率 > 5%、平均响应时间 > 10s、单日调用费用超过阈值时触发告警。

8.2 关键关系

  • 一个长期目标可以有多个中期目标；中期目标可以继续拆成短期目标。
  • 一个目标可以关联多个项目，一个项目包含多个任务（MVP 阶段）。
  • 习惯独立于目标体系，但可通过 goal_habit_link 关联表选择性绑定到目标。
  • 任务可以关联一个或多个日程事件，但要避免重复计算。
  • 打卡记录只记录实际发生的执行事实，支持同时关联任务和习惯（或两者之一）。
  • 提醒（Reminder）可绑定到目标、任务或习惯，支持多渠道（推送、应用内、邮件）。
  • AI 计划生成结果先进入 PlanVersion，用户确认后再批量生成业务实体。
  • AISession 与 AIOperation 为一对多关系，会话上下文通过摘要机制控制长度。
  • UserEvent 为独立分析表，不直接参与业务逻辑，仅用于产品漏斗和留存分析。

9. API 设计建议

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

9.1 用户与目标

  • POST /api/goals 创建目标。
  • GET /api/goals/:id 获取目标详情和进度。
  • PATCH /api/goals/:id 修改目标。
  • POST /api/goals/:id/recalculate 重新计算进度。

9.2 任务与打卡

  • POST /api/tasks 创建任务。
  • GET /api/tasks?date=YYYY-MM-DD 获取当天任务。
  • POST /api/tasks/:id/complete 完成任务。
  • POST /api/tasks/:id/postpone 延期任务。
  • POST /api/checkins 写入打卡记录。
  • GET /api/checkins/calendar 获取打卡日历。

9.3 AI 计划

  • POST /api/ai/plan-drafts 根据目标和约束生成计划草案。
  • GET /api/ai/plan-drafts/:id 获取草案。
  • POST /api/ai/plan-drafts/:id/approve 用户确认计划。
  • POST /api/ai/replan 基于执行情况生成调整方案。
  • POST /api/ai/review 生成日 / 周复盘。

9.4 API 设计原则

  • 所有写接口支持幂等键，避免弱网重试造成重复任务。
  • AI 接口返回 request_id，长任务通过轮询、SSE 或 WebSocket 获取状态。
  • 所有计划变更记录审计日志。
  • 业务接口不直接暴露模型供应商的原始返回格式。

10. MVP 迭代路线

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

阶段 0：原型验证

目标是验证核心流程，而不是先堆功能：

  • 今日页、目标页、任务页、计划草案页。
  • 完成任务后的进度反馈。
  • 一次 AI 生成计划的完整交互。
  • 用假数据验证 7 日执行闭环。
  • 预置 5 个高质量领域模板（如考研英语、减脂入门、晨间习惯等），解决冷启动空状态问题，验证模板匹配 + AI 微调流程。

阶段 1：MVP

建议包含：

  • 用户登录与基础设置（含精力曲线配置）。
  • 长 / 中 / 短期目标。
  • 项目、任务、子任务、截止日期。
  • 独立习惯模块与习惯打卡。
  • 今日视图与简单日历。
  • 周期任务。
  • 每日打卡、连续记录、目标进度。
  • AI 生成计划草案并人工确认（基于领域模板）。
  • 基础提醒和周复盘。
  • 执行偏差记录（实际耗时、质量评分、阻塞原因）。

阶段 2：增强执行

  • 离线模式与多端同步。
  • 更强的重复规则。
  • 时间块、番茄钟和专注记录。
  • 计划负载检测、延期分析。
  • 目标模板和行业计划模板。
  • 统计报表与数据导出。

阶段 3：智能化与生态

  • 基于长期行为的个性化计划。
  • 多模型路由与成本控制。
  • 日历、邮件、运动或知识库等外部服务集成。
  • 共享目标、家庭计划或小组挑战。
  • 面向教练、老师或企业的计划管理能力。

11. AI 成本、稳定性与安全

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

11.1 成本控制

  • 普通任务拆解优先调用低成本模型。
  • 复杂目标规划、周复盘使用更强模型。
  • 对用户资料和历史任务做摘要，避免每次传入完整上下文。
  • 缓存相同输入的计划建议，但要考虑日期和执行状态变化。
  • 对 AI 调用设置每日额度、超时和降级策略。

11.2 稳定性

  • 模型响应必须经过 JSON Schema 校验。
  • 解析失败自动重试一次，并降低输出复杂度。
  • 计划写入采用事务：目标、里程碑、任务和日程要么全部成功，要么全部回滚。
  • AI 生成与业务落库解耦，避免模型波动影响核心任务功能。

11.3 隐私与安全

  • 最小化收集个人信息，敏感数据加密存储和传输。
  • 用户明确同意后才将个人计划和行为数据发送给模型服务。
  • 提供删除数据、导出数据和关闭 AI 的选项。
  • 不把健康、心理、财务等高敏感领域的建议包装成专业结论。
  • 记录模型版本、提示词版本和计划变更，方便追溯。
  • 数据保留与合规：打卡记录默认保留 2 年，删除账号后 30 天内清除所有个人数据；向模型供应商传输数据前进行脱敏处理，签署 DPA（数据处理协议）。
  • 内容安全：涉及健身/饮食/用药建议时，AI 输出必须附带免责声明（“本建议仅供参考，不构成专业医疗意见”）；高风险内容触发人工复核机制。
  • 本地优先：敏感计划数据优先本地存储，仅在需要 AI 生成计划时上传必要摘要，降低数据暴露面。

12. 关键产品决策

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

  1. 先做“可执行计划”，再做“万能 AI 助手”。 AI 的第一价值应是把目标拆成用户今天能做的动作。
  2. AI 只生成草案，用户确认后生效。 这是信任和可控性的基础。
  3. 目标进度与任务完成率分开。 完成很多小任务不一定代表目标真正推进。
  4. 打卡记录采用事实事件模型。 便于补记、统计、纠错和多端同步。
  5. 首页只突出少量重点。 如果同时展示几十个任务，用户会回到“任务堆积”问题。
  6. MVP 不要一开始做社交、复杂积分和多模型编排。 先验证用户是否能持续完成计划。
  7. 习惯必须独立于任务体系。 日常作息、饮食、运动等持续性行为不天然属于某个项目，缺失习惯维度的计划工具只是高级待办清单。
  8. 能量管理是排程的核心约束之一。 时间可用 ≠ 能高效执行，必须将精力曲线纳入 AI 排程逻辑。
  9. 模板匹配优先于纯生成。 MVP 阶段用预置领域模板解决冷启动和输出稳定性问题，比从零生成的成本更低、质量更可控。
  10. 量化偏差才能量化进步。 只记录“完成/未完成”无法支撑 AI 调优，必须记录耗时偏差、质量评分和阻塞原因。

13. 推荐的首个版本范围

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

如果由一个小团队开始，第一版建议只聚焦一个核心闭环：

创建目标 → AI 生成 7 天计划 → 用户确认 → 今日执行 → 每日打卡 → 看到进度 → 周末复盘 → AI 调整下一周计划。

首个版本可以暂不实现：复杂协作、公开社区、跨平台日历双向同步、重度游戏化、复杂知识库和完全自动化排程。只要上述闭环能稳定运行，就具备继续扩展的产品基础。

补充：习惯模块纳入 MVP 的必要性

对于个人用户而言，目标（如“考研上岸”）是阶段性事件，而习惯（如“每日背词”“23:00 前睡”）是持续性支撑。如果 MVP 只包含目标-任务体系，用户在目标间隙期会失去使用动力。建议阶段 1 就包含：

  • 独立习惯列表与每日习惯打卡。
  • 习惯与目标的可选关联（如“每日背词 50 个”同时服务于“通过四级”目标）。
  • 习惯连续记录与最低完成标准（如“至少背 30 个”即算打卡成功）。

这样即使在没有明确短期目标的时间段，用户仍有每日打开 App 的理由。

14. 结论

本节对该主题进行进一步拆解，便于产品、设计与研发协同。

这款 App 的竞争力不在于“功能比待办工具多”，而在于能否让用户更容易开始、更容易坚持，并且在计划不现实的时候及时调整。技术上应采用结构化计划对象、版本化审批、事件化打卡和模型适配层；产品上应围绕目标拆解、每日执行和复盘反馈形成连续体验。

建议下一步按以下顺序推进：

  1. 先确定一个主场景，例如备考、健身或个人成长，不要一开始覆盖所有人群。
  2. 画出 5 个核心页面：今日、目标详情、任务编辑、AI 计划草案、周复盘。
  3. 用假数据完成前端交互原型。
  4. 接入一个模型供应商，先跑通结构化 JSON 计划生成和人工确认。
  5. 通过 5—10 名真实用户验证首周计划完成率，再决定是否扩展更多功能。
